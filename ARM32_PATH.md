# Fireman 1.0.9 — путь к запуску на TECNO LJ7

Дополняет `DIAGNOSIS.md`. Здесь — что делать, и почему это сработает.

---

## 1. Ваш тест закрыл диагностику

`Fireman_ARM32_Install_Probe.apk` (чистая Java + **одна** библиотека
`lib/armeabi-v7a/`) не установился с той же ошибкой. Пробник без библиотек
устанавливался. **Разница ровно одна — наличие 32-битной библиотеки.**

Причина подтверждена на физическом устройстве: Package Manager отвергает APK,
потому что прошивка не объявляет ни одного 32-битного ABI. Это не Play Protect
и не targetSdk.

## 2. Новое: блокировка НЕ в железе и НЕ в ядре

Я скачал стоковый образ ядра для LJ7 из community-репозитория прошивки
(`device_tecno_LJ7-kernel`, ветка `lineage-23.2`, файл `Image.gz`) и извлёк
встроенный конфиг ядра — маркер `IKCFG_ST` → zlib → `lj7_kernel.config`.

Версия ядра в образе:

```
Linux version 6.1.115-android14-11-g6b18f0b574ab-ab12901745
```

Это **точно** та версия, что стоит на вашем аппарате (совпадает с базой
Device Info HW для TECNO LJ7). То есть конфиг ниже — про ваше ядро.

Ключевые опции:

| Опция | Значение | Что значит |
|---|---|---|
| `CONFIG_COMPAT` | `=y` | ядро **исполняет** 32-бит код (AArch32 EL0) |
| `CONFIG_COMPAT_BINFMT_ELF` | `=y` | ядро **запускает** 32-бит ELF-файлы |
| `CONFIG_KUSER_HELPERS` | `=y` | есть страница kuser-хелперов для 32-бит процессов |
| `CONFIG_COMPAT_VDSO` | `=y` | есть 32-бит vDSO |
| `CONFIG_ARM64_4K_PAGES` | `=y` | страницы 4 КБ |
| `CONFIG_ARM64_VA_BITS` | `=39` | 39-битное адресное пространство |

Плюс ядра LJ7 — Cortex-A78 и Cortex-A55, оба умеют AArch32 (ARM KA006014,
категории 4 и 3).

**Вывод, который меняет картину.** Блокировка находится **только в userspace**:
в прошивке нет 32-битного `zygote` и 32-битных системных библиотек, поэтому
Package Manager не предлагает 32-битный ABI. Но ядро под ним способно исполнить
32-битный код нативно, без эмуляции и без трансляции.

Это важно ещё и потому, что опция `CONFIG_ARM64_4K_PAGES=y` совпадает с
выравниванием библиотек игры: все шесть `.so` в APK — ELF32 с `p_align=4096`.

## 3. Что из этого следует

Раз ядро умеет 32-бит, **любая среда, которая приносит свой 32-битный Android
userspace, может запустить игру нативно**. Это не эмуляция процессора: код
исполняется на тех же ядрах, что и остальная система.

Это единственный путь без пересборки игры. Обратите внимание: попытка «починить»
APK (подпись, выравнивание, манифест) уже сделана и к цели не приводит —
она не добавляет `arm64-v8a`, а без 32-битного `linker` даже принудительно
установленный APK не загрузит свои библиотеки.

## 4. Решение A — среда с 32-битным userspace (без пересборки)

Приложения-виртуализаторы Android (VMOS Pro, VPhoneOS, F1 VM, X8 Sandbox)
запускают гостевой Android как процесс внутри вашей системы. Гостевая система
использует **то же ядро**, а оно, как показано выше, 32-бит исполняет. Поэтому
гостевой 32-битный Android в них работоспособен.

Порядок:

1. Поставить один из виртуализаторов (VPhoneOS или VMOS Pro).
2. Создать гостевую систему с Android 7.1.2 — это последняя версия, где 32-битный
   userspace массово использовался, и игра (targetSdk 27) там чувствует себя
   роднее всего.
3. В настройках гостевой системы выбрать режим архитектуры
   **«64-bit & 32-bit mixed»**, если такой пункт есть.
4. Внутри гостя установить **`Fireman_1.0.9_full_original.apk`** — полный
   оригинал 31 МБ с подписью Magma Mobile.

Почему именно оригинал, а не `final.apk`: подпись Magma Mobile подлинная, и в
гостевой системе не будет конфликта с другими копиями игры. Если планируете
ставить в одной гостевой системе и оригинал, и пересобранные варианты — учтите,
что они подписаны **разными** ключами и одновременно не установятся
(конфликт подписей), но package name у них одинаковый, так что нужен только один.

Что ожидать по производительности: игра 2016 года с Unity 5.3.8 и простой
графикой. Внутри виртуализатора будет накладной расход, но для такой игры его
должно хватить.

## 5. Решение B — пересборка под arm64 (если A не подойдёт)

Восстановленный Unity-проект лежит в релизе
(`Fireman_Unity_Project_recovered.zip`, 299 C#-файлов, 6 сцен, 70 префабов).
Путь такой:

1. Установить Unity Hub и Unity **2017.4.16 LTS** или **2018.2+** — это первые
   версии с поддержкой arm64 для Android (в 5.3.8 её нет и быть не может).
2. Открыть восстановленный проект, дать ему доимпортировать ассеты.
3. Player Settings → Scripting Backend = **IL2CPP**, Target Architectures →
   включить **ARM64**.
4. Собрать, подписать, протестировать.

Сложности, которые надо знать заранее: NGUI восстановлен как исходники
(130 скриптов), и часть их может не собраться на новом Unity без правок;
шрифты и материалы из AssetRipper иногда требуют ручной перенастройки;
сторонние SDK (Advertisements, Google Analytics) лучше отключить.

Это существенно большая работа, чем вариант A, поэтому начинать с неё не нужно.

## 6. Решающий тест: умеет ли 32-бит именно ваше ядро

Всё выше опирается на конфиг ядра, снятый с образа прошивки. Это надёжно, но
проверяется прямо на телефоне — и я собрал для этого отдельный APK.

```
Fireman_ARM32_Exec_Test.apk
```

Что он делает: не содержит нативных библиотек (значит, ставится всегда), внутри
два крошечных статических исполняемых файла и кнопка отчёта:

- `armprobe32.bin` — ELF32/ARM, единственная инструкция: `exit_group(42)`
- `armprobe64.bin` — ELF64/AArch64, `exit_group(43)` — контроль

APK копирует их в свой каталог, ставит бит выполнения, запускает оба и печатает
коды возврата. Плюс читает `/proc/config.gz`, если он доступен приложению
(в ядре `CONFIG_IKCONFIG_PROC=y`), и показывает строки `CONFIG_COMPAT*`.

Как читать результат:

| 32-бит | 64-бит | Вывод |
|---|---|---|
| 42 | 43 | ядро исполняет 32-бит → решение A сработает |
| ошибка | 43 | ядро отказывает в 32-бит → только решение B |
| ошибка | ошибка | exec закрыт и на targetSdk 28 — политика вендора, пришлите экран |

Первый прогон на вашем аппарате вернул `error=13, Permission denied` при
`mode=executable` — это была моя ошибка в сборке, а не отказ ядра. Причина
разобрана ниже, тест пересобран.

### 6.1. Первая сборка дала `error=13` — и это была моя ошибка, а не ядра

Первый прогон вернул:

```
could not run: IOException: Cannot run program
".../files/probe/armprobe32.bin": error=13, Permission denied
note: ; mode=executable
```

Бит выполнения стоял, файл читался, но `execve` вернул `EACCES`. Причина — в
SELinux, и она точная.

Домен приложения Android выбирает **по `targetSdk`** (файл `seapp_contexts`):

```
minTargetSdkVersion=34 → untrusted_app
minTargetSdkVersion=29 → untrusted_app_29
minTargetSdkVersion=28 → untrusted_app_27
```

Право на запуск своего файла есть только у «старых» доменов:

```
untrusted_app_27.te:  allow untrusted_app_27 app_data_file:file execute_no_trans;
untrusted_app_all.te: allow untrusted_app_all app_data_file:file { r_file_perms execute };
```

То есть `untrusted_app_29` и выше получают лишь `execute` без `execute_no_trans`,
а для запуска процесса нужен именно `execute_no_trans`. Отсюда отказ при
`targetSdk 34`, с которым был собран первый вариант.

Я пересобрал тест с `targetSdk 28` (ровно так же поступает Termux, который
запускает свои бинарники именно поэтому). Проверил на ветке `android16-release` —
версии, соответствующей вашему аппарату:

- `targetSdk 28` → `untrusted_app_27` → правило `execute_no_trans` **есть**;
- `MIN_INSTALLABLE_TARGET_SDK = 24`, значит установка при `targetSdk 28`
  **не блокируется** (порог Android 16 — API 24, а не 28).

Сборка: `minSdk 24`, `targetSdk 28`, `versionCode 2`, без `lib/`, подпись v2+v3.

Файлы я собрал вручную на Python (скрипт `scripts/make_probe_elfs.py`), потому что
кросс-компилятора в этой среде нет. Корректность проверена `readelf` и разбором
инструкций: `mov r7,#248; mov r0,#42; svc #0` для ARM и
`movz x0,#42; movz x8,#94; svc #0` для AArch64, оба — статические PIE с
`p_align=0x1000`, единственный `PT_LOAD` с нулевым смещением.

## 6.2. Результат на вашем аппарате: 32-бит работает

Экран вашего прогона:

```
targetSdk of this app: 28
SELinux domain: u:r:untrusted_app_27:s0:c96,c258,c512,c768

32-bit (ELF32/ARM, exit 42):        exit code: 42   <- expected, execution worked
64-bit control (ELF64/AArch64, exit 43): exit code: 43   <- expected, execution worked
```

Что это доказывает, по пунктам:

- **Домен `untrusted_app_27`** — ровно тот, что нужен: `targetSdk 28` сработал,
  и exec был разрешён политикой, а не вопреки ей.
- **Код 42** вернул именно 32-битный ELF32/ARM. Процесс реально стартовал и
  дошёл до `exit_group(42)`. Если бы ядро не умело AArch32, `execve` вернул бы
  `ENOEXEC` (`error=8`) ещё до запуска, и никакого кода возврата не было бы.
- **Код 43** — контрольный 64-бит, подтверждает, что механизм запуска исправен.

То есть вопрос закрыт **измерением, а не только конфигом ядра**: `CONFIG_COMPAT=y`
и живой прогон 32-битного бинарника говорят одно и то же.

Заодно экран показал две вещи, которые подтверждают диагноз про userspace:

```
32-bit runtime files:   none present
64-bit runtime files:   /system/bin/linker64, /system/lib64/libc.so, ...
zygote: zygote64   abilist: arm64-v8a
```

В прошивке нет ни `linker`, ни `libc.so` в 32-битном варианте — поэтому
Package Manager и не предлагает 32-битный ABI. Ядру это не мешает, а вот
системе приложений — мешает.

## 7. Что осталось непроверенным

- **Виртуализаторы я не тестировал.** Теперь доказано, что ядро исполняет
  32-бит, но конкретное приложение (VMOS Pro, VPhoneOS, F1 VM) может добавить
  свои ограничения на Android 16: требования к аккаунту, лицензии, ограничения
  на установку APK извне, поведение на HiOS. Проверять надо на устройстве.
- **Эмулятор в этой среде недоступен.** `/dev/kvm` нет, arm64-образ эмулятор
  отвергает на x86_64-хосте. Это ограничение среды, на вывод не влияет.
- **Сама игра внутри гостевой системы ещё не запускалась.** Успешный exec
  32-битного бинарника — необходимое условие, но не доказательство, что Unity
  5.3.8 запустится в конкретном виртуализаторе.

## 8. Итог

- Причина отказа при установке: **доказана** на устройстве (нет 32-битного ABI).
- Ядро 32-бит поддерживает: **доказано дважды** — конфиг (`CONFIG_COMPAT=y`,
  build id совпадает с вашим аппаратом) и **живой прогон** (`exit code 42`).
- Ограничение: **только userspace** — нет 32-битного `linker`, `libc.so` и
  зиготы (подтверждено сканированием файлов на экране).
- Рабочий путь без пересборки: **виртуализатор с 32-битным гостевым Android**.
- Путь с пересборкой: **Unity 2017.4.16 / 2018.2+ с IL2CPP и ARM64**.
- Тест на телефоне: **`Fireman_ARM32_Exec_Test.apk`** — пройден, результат выше.
